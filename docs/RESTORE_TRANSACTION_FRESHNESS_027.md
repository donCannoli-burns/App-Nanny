## Bounded repair contract

The Restore pipeline retains strict JSON/UTF-8/ZIP member verification, canonical saved-state admission, authority conflict adjudication, and the existing atomic Restore commit. Only **the temporal authorization of async Restore continuations** changes:

- A monotonic `restoreTransactionGeneration` is advanced when a new Restore starts, when Generate captures an import attempt, and when an authority dialog opens or closes.
- At Restore start, the operation captures its generation, exact state-object identity, editable scaffold text, file-picker editor/selection generations, a project-state fingerprint, and a templates fingerprint.
- The shared `restoreTransactionIsCurrent(tx)` predicate must hold after the original file read and after ZIP or standalone JSON checksum verification, and immediately before the synchronous Restore dialog/commit.
- Stale failures are suppressed by checking the **same predicate** inside `catch`, so old errors cannot replace newer authority status.
- A Restore cannot begin while `pendingAuthorityTask` is non-null.
- Project-state fingerprinting excludes only the top-level `planning` object and `updatedAt`, which are subject to timer-only autosave bookkeeping. The remaining project state, editor generations/text, state identity and templates must remain unchanged. This avoids a false abort found during local testing after an ordinary autosave.
- A newer Restore selection supersedes any previous pending Restore.

The final check and `commitRestoredProject()` execute in the same JavaScript turn, with **no await** between freshness admission and mutation. Restoration itself remains conditional on original ZIP or JSON verification.
